# TWOYEARSOLD エコシステム 設計

2026-10-14。オーナーとの対話で決めた内容をまとめた設計。実装の計画はこの文書の承認後に別に書く。

## 1. 目的と前提

次の輪を、できるかぎり自動で回す。

1. アプリを作る・改良する
2. バグを潰し、機能を極限まで高める
3. iOS / Android 向けにリリースする
4. 利用者の反応を得て、市場を調べ、ニーズをつかむ
5. 1 へ戻る

アプリの量産が目的ではない。次の哲学を前提にする。

- 作るべきアプリと作るべきでないアプリの判定は、人がする。
- 究極的に美しいデザイン。
- 市場に対して相対的に最も高い性能と、機能・モードの網羅。
- 広告なし、買い切り。

対象は現在の 9 作(NumberPlace / 2048 / AirHockey / FreeThrow / Cover Three / Minesweeper / PK / Reversi / Solitaire)と、今後人が「作る」と決めたアプリ。

## 2. 決定の一覧

| 項目 | 決定 |
|---|---|
| 人の関わり方 | 要所だけ承認する。それ以外は自動で進め、報告を届ける |
| 人が承認する箇所 | 新しいアプリの着手 / 見た目の大きな変更 / 価格 / アプリごとの最初の公開 |
| 更新版の公開 | 合格基準を満たせば、審査への送信と公開まで自動で行う |
| 反応の集め方 | アプリ外の情報に加えて、同意した人の匿名の利用統計を取る |
| 対象年齢 | 13 歳以上 |
| 進め方 | 仕組みを先に設計する(この文書) |
| 構成 | 専用機を置く。当面はオーナーの Mac(MacBook Pro M5 Pro / 24GB / 1TB)を兼用し、夜間の運用で困ったら Mac mini を足す |
| 開発者アカウント | 個人のまま始める。組織アカウントへの移行を検討する(オーナーは個人事業主) |
| iOS | 設計に含める。着手は Android の次 |
| 市場との比較 | 合否に入れる(公開の条件) |
| 拠点 | twoyearsold.net。識別子は `net.twoyearsold.<名前>`、サイトは `<名前>.twoyearsold.net`、連絡先は `support@twoyearsold.net` |

## 3. 全体像

### 3.1 5 つの部品

1. **憲章**: 判断の基準を書いた文書。
   - `DESIGN.md`(見た目・所作・声と用語)。既存。
   - 製品の憲章(新設)。4 つの哲学、作る・作らないを判断する材料の出し方、価格の考え方、権利の確認手順を書く。
2. **台帳**: アプリごとの状態の記録。運用用の非公開リポジトリ `twoyearsold-ops` に置く。
3. **段**: 「作る・改良」「品質」「リリース」「反応・市場」の 4 つ。それぞれに、始める条件、合格基準、残す成果物を決める。
4. **運転**: 専用機での予定実行。毎晩、台帳を読んで進められる段を進め、報告を残す。
5. **承認の窓口**: 決めた箇所で止まり、台帳に「承認待ち」と書く。オーナーは報告を読んで、承認か差し戻しを返す。

### 3.2 一周の流れ

1. 市場を調べ、候補と根拠を出す。
2. 【人】作る・作らないを決める。
3. 作る・改良する。
4. 【人】見た目の大きな変更があれば確認する。
5. 品質の合格基準をすべて満たすまで直す。
6. ストアに出す準備をする(ビルド、掲載情報、申告、権利の確認)。
7. 【人】価格を決める。そのアプリの最初の公開であれば、公開を承認する。
8. ストアへ出す(更新版は自動)。
9. 反応を集める。
10. 改良の候補を台帳に積み、3 へ戻る。新しいアプリの候補は 1 へ戻る。

### 3.3 台帳の形

アプリごとに 1 ファイル(`ledger/<アプリ>.md`)。次の項目を持つ。

- **現在の段**と、その段に入った日。
- **公開の状態**: Web / Android / iOS それぞれの公開中の版、テスト中の版。
- **次の一手**: 次の実行で行う作業を 1 つ。
- **課題**: 未解決の不具合と改良の候補。それぞれに根拠(どの検査・どのレビュー・どの数字から出たか)を付ける。
- **承認待ち**: オーナーの判断が要る事項。判断に必要な材料を添える。
- **人の作業**: オーナーにしかできない操作。手順を添える。
- **未検証の前提**: この設計で仮定していて、まだ実物で確かめていないこと。

変更はすべて commit として残す。予定実行は前回の記憶を持たないので、台帳だけを読めば続きができる書き方にする。

## 4. 品質の段

合格基準は 3 層。3 層すべてを満たした版だけが、リリースの段へ進む。

### 4.1 第 1 層: 機械検査(既存に足す)

- 解析(`flutter analyze`)、全テスト。
- 品質ガード(`quality_guard.py`)、翻訳ガード(`i18n_guard.py`)。
- ゴールデン、画面の巡回(ホームから 2 操作先までの当たり判定)。
- **権利の検査(新設)**:
  - 使ってはいけない語の辞書。表示される文字列、掲載文、サイトの文面を対象に検査する。初期の辞書は Sudoku、数独、Othello、オセロ、Gobblet、Tetris。
  - 同梱フォントと利用パッケージのライセンス表示があること。

### 4.2 第 2 層: 実機相当での検査(新設)

2026-10-13 に Android のエミュレータで見つかった 4 件(横向きで盤が消える、起動直後の白い画面、文字拡大での折り返し、低い画面でボタンが切れる)は、第 1 層をすべて通過していた。これを拾う層。

- Android のエミュレータと iOS のシミュレータに、リリース用のビルドを入れる。
- 起動から主要な画面までを自動でたどる。
- 次の条件を組み合わせて、各画面を撮る。
  - 画面の向き(縦・横)
  - 文字の拡大(1.0 倍・1.3 倍)
  - 言語(英語・日本語・アラビア語を必須、ほかは巡回)
  - 画面の大きさ(小さい端末・標準・大きい端末)
  - テーマ(明・暗)
- 撮った画面から、文字やボタンの切れ・重なり・はみ出しを検出する。
- 次の時間を測り、上限を超えたら不合格にする。
  - 起動から最初の画面まで
  - 主要な処理(NumberPlace なら出題)にかかる時間
  - 画面が止まる時間の最大値
- 効果音の再生が要求されていることを確かめる。

実機での検査は、実機が用意でき次第この層に足す。

### 4.3 第 3 層: 市場との比較(新設)

「相対的に最も高い性能と、機能・モードの網羅」を、公開の条件として確かめる。

- **比べる相手**: 同じジャンルで、Google Play と App Store の上位に入っているアプリ。日本と米国のストアから、あわせて 10 本を初期値とする。
- **機能とモードの一覧表**: 相手が持つ機能とモードを洗い出し、自作が持っているかを突き合わせる。
- **網羅から外すもの**: 広告、アプリ内課金、通信が前提の機能、他社の商標に依存する機能。哲学に反するので対象外とし、外した理由を台帳に残す。
- **性能の比較**: 起動の速さと、主要な処理の速さを同じ条件で測って比べる。
- **合格**: 外したものを除く機能とモードをすべて持ち、性能の各項目で相手の最良値を上回ること。

比べる相手は、リリースの準備に入るたびに選び直す。

NumberPlace の 1.2.0 はクローズドテスト版として出す。第 3 層は製品版の公開までに満たす。

## 5. リリースの段

### 5.1 機械化するもの

- **ビルドと署名、バージョン番号の採番**。ストアで公開済みの番号を読み、続きの番号を付ける。
- **掲載用の画面の撮影**。エミュレータ / シミュレータで、決めた画面を言語ごとに撮る。
- **掲載文と申告の管理**。各アプリの `store/` にある内容を正とし、ストア側との差分を検出する。
- **ストアへの登録**。Google Play Developer API と App Store Connect API を使い、ビルドのアップロードと掲載情報の更新を行う。ブラウザの画面操作は使わない。
- **Web 版**。push で公開し、公開後にオフライン起動まで自動で確かめる。

### 5.2 更新版の自動公開

承認済みのアプリの更新版は、審査への送信と公開まで自動で行う。

公開を実行するのは、合格基準をすべて満たしたときにだけ動く、決まった手順(ストアの API を呼ぶワークフロー)とする。Claude がその場の判断で公開を実行する形にはしない。Claude は手順と合格基準を整え、結果を報告する。

安全装置を次のとおり置く。数値は初期値で、運用しながら調整する。

- **合格基準**: 品質の 3 層をすべて通った版だけが公開へ進む。
- **段階的な公開**: 利用者の 10% に配り、24 時間問題がなければ 50%、さらに 24 時間で 100% にする。
- **自動停止**: 次のどちらかで配信の拡大を止め、報告する。
  - クラッシュのない利用者の割合が、前の版より 0.5 ポイント以上下がった。
  - 24 時間のうちに、星 1〜2 のレビューが 3 件以上付いた。
- **見た目の差分**: ゴールデンで 1 画面あたり 2% を超える差分がある版、または画面が増えた版は「見た目の大きな変更」とみなし、承認待ちに回す。
- **戻す手順**: 前の版へ戻す手順を用意しておく。
- **頻度**: 1 つのアプリにつき、公開は 1 日 1 回まで。

### 5.3 人の作業として残すもの

- 価格の決定と変更。
- アプリごとの最初の公開の承認。
- 規約への同意、削除、外部のコミュニティへの投稿。
- 個人アカウントの間の、12 人で 14 日間のクローズドテスト。Google グループ `twoyearsold-android-apptesters` に常連のテスターを維持し、新しいアプリのたびに参加してもらう。
- 資格情報にあたるファイル(証明書など)のアップロード。

### 5.4 開発者アカウント

- **個人のまま始める**。新しいアプリを Google Play に出すたびに、クローズドテストが要る。
- **組織アカウント**: 条件は、D-U-N-S 番号(無料、取得に最大 30 日)、確認済みの公式サイト、公開される電話番号とメール。個人から組織への種別変更は Play Console からできる。組織用の支払いプロファイルを新しく作る。
- 組織アカウントにできると確かめられたら、移行の手順を台帳の「人の作業」に出す。

### 5.5 iOS

- Apple Developer Program への登録(年 99 米ドル、オーナー本人)。
- ビルドと署名は専用機で行う。
- 審査への提出、段階的な公開、レビューの取得は App Store Connect API で行う。
- 着手は、NumberPlace の Android 版がクローズドテストに入ってから。

## 6. 反応・市場の段

### 6.1 集める情報

1. ストアのレビューと評価。
2. 販売数、返金、クラッシュ報告(ストアが標準で出すもの)。
3. `support@twoyearsold.net` に届くメール。
4. 同意した人の匿名の利用統計。
5. 競合の動き(新作、更新、価格)。

### 6.2 匿名の利用統計

- **既定ではオフ**。設定画面の「改善に協力する」をオンにした人だけが送る。
- **送るもの**: 遊ばれたモード・盤の大きさ・難易度、完了した割合、ヒントの使用回数、選ばれているテーマと言語、アプリと OS の版。
- **送らないもの**: 氏名やメールなど個人を特定する情報、端末の識別子、広告 ID、位置情報。利用者ごとの通し番号も付けない。
- **送り方**: 日ごとの集計にまとめて送る。操作の 1 つ 1 つは送らない。
- **送り先**: 自前の受け口 `stats.twoyearsold.net`。受け取って集計を保存するだけの小さな仕組みとし、Cloudflare Workers と D1 を初期の候補とする。第三者の解析部品はアプリに入れない。
- **あわせて変えるもの**: 統計を入れる版から、通信の権限、掲載文、プライバシーポリシー、データセーフティの申告を「既定では収集しない。同意した場合のみ匿名の統計を送る」に改める。売りは「広告なし・追跡なし」とする。

### 6.3 輪へ戻す

- 週に 1 度、集めた情報を要約する。
- 改良の候補を、根拠を付けて台帳の「課題」に積む。
- 新しいアプリの候補は、市場調査の報告としてオーナーへ出す。作る・作らないはオーナーが決める。

## 7. 運転

### 7.1 予定実行

- 専用機で、毎晩 2:00 に実行する。
- 1 回の実行で、各アプリの台帳の「次の一手」を進める。
- 失敗したら台帳に記録して止まる。同じ作業を勝手にやり直さない。
- 仕組みは台を移せる形で作る。台に固有の設定は 1 か所にまとめる。

### 7.2 報告

- 毎朝、報告を 1 つ残す(`reports/YYYY-MM-DD.md`)。
- 中身は、進めたこと、承認待ちの事項、オーナーにしかできない作業、主な数字(販売数、評価、クラッシュ、検査の結果)。
- `twoyearsold-ops` へ push し、リポジトリの通知でオーナーに届ける。

### 7.3 自動実行に許す範囲

| してよい | しない |
|---|---|
| コードの修正とテスト | 価格の変更 |
| commit と push | 削除 |
| Web 版の公開 | 規約への同意 |
| ストアへのビルドと掲載情報の登録 | 外部のコミュニティへの投稿 |
| 承認済みアプリの更新版の公開(5.2 の手順による) | アプリごとの最初の公開 |
| 調査と報告 | 新しいアプリの着手 |

### 7.4 鍵と API キー

- リポジトリの外の決まった場所(`~/keystores/` など)に置く。
- 報告、ログ、台帳に出さない。
- バックアップはオーナーが別の場所に取る。

## 8. 設備と費用

| 項目 | 費用 | 時期 |
|---|---|---|
| 専用機(オーナーの Mac を兼用) | 0 円 | 今 |
| Apple Developer Program | 年 99 米ドル | iOS に着手するとき |
| 統計の受け口 | 小さい見込み | 統計を入れる版 |
| D-U-N-S 番号 | 無料 | 組織アカウントにできると確かめられたら |
| 実機(Android・iPhone) | 手持ちがあれば 0 円 | 実機での検査を始めるとき |

## 9. 未検証の前提

この設計で仮定していて、まだ実物で確かめていないこと。実装の計画では、これらを確かめる作業を先に置く。

1. Google Play Developer API だけで、更新版の審査への送信と段階的な公開まで完了できる。
2. 段階的な公開と配信の停止が、有料アプリと個人アカウントでも使える。
3. 個人から組織へ種別を変えたアカウントで、クローズドテストの要件が外れる。
4. 個人事業主が D-U-N-S 番号を取り、組織アカウントを作れる。
5. iOS の署名、審査、段階的な公開の手順。
6. 統計の受け口の費用が小さく収まる。
7. エミュレータ / シミュレータでの自動巡回と、撮った画面からの崩れの検出が、誤検出の少ない精度で作れる。
8. オーナーの Mac を兼用して、毎晩の実行が安定して回る。
9. NumberPlace のアップロード鍵のリセットが承認される(2026-10-13 に申請済み)。

## 10. この設計に含めないもの

- 各アプリの個別の機能追加の中身(台帳の「課題」として扱う)。
- 新しいアプリの企画(市場調査の報告を受けてオーナーが決める)。
- 価格の戦略。

## 11. 実装の分け方

全体は 1 つの計画には大きいので、次の 4 つに分けて、それぞれ計画を書いて実装する。順番はこのとおりとする。

1. **台帳と運転**: `twoyearsold-ops` リポジトリ、台帳の形、毎晩の実行、朝の報告。ほかの 3 つの土台になる。
2. **品質の第 2 層と第 3 層**: 実機相当での検査、市場との比較、権利の検査。
3. **リリースの機械化**: ビルドと採番、掲載用の画面の撮影、ストアの API での登録、更新版の自動公開と安全装置。Android を先に作り、iOS を続ける。
4. **匿名の利用統計**: アプリ側の同意と集計、受け口、掲載文・ポリシー・申告の更新。

各計画の最初に、第 9 節の未検証の前提のうち、その計画に関わるものを確かめる作業を置く。
