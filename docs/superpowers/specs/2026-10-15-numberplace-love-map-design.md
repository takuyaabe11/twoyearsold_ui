# 愛の地図(NumberPlace) 設計

2026-10-15。旧仕様 `2026-10-14-numberplace-yardstick-design.md`(市場の上位との比較)を置き換える。全体の設計(`2026-10-14-ecosystem-design.md`)の第 2 節「品質の段」のうち、3 層目「市場との比較」の考え方も、この仕様で置き換える。1 層目(機械検査)と、旧仕様で作った入口・権利の語の検査・性能の道具は、そのまま使う。

## 1. 目的

ナンプレを愛する人たちが何を愛しているのかを調べ、観点の地図にまとめる。そのうえで、自作の NumberPlace がそれぞれの観点にどれだけ応えているかを確かめる。応えていない所が、次の改良の材料になる。

オーナーの言葉(2026-10-15): 「そもそもアプリとだけ比較することが間違えているのかもしれません。例えばナンバープレイスを愛する人たちが何を愛しているのかを追求することなんじゃないでしょうか」

## 2. 経緯

- 旧仕様は、市場の上位 10 本と機能・性能を比べ、「線の内側の機能をすべて持ち、性能で最良値を上回る」ことを合格にしていた。
- 上位 9 本を実際に触ると、作りの中心は広告とつなぎ止めの仕掛けだった。起動直後の全画面の広告、広告の動画と引き換えのヒント、経験値とリーグ、通知の催促、何枚も続く同意の画面などである。
- 機能の網羅を目指すと、自作の方針(DESIGN.md §0。静か・買い切り・広告なし・完全オフライン)に反する方向へ押される。性能も、相手が広告や通信で遅いだけなので、上回っても意味が薄い。
- オーナーは測定を止め、方針から話し直すと決めた。

## 3. オーナーの決定(2026-10-15)

- **誰の愛を追うか**: 3 つの層すべて。毎日の楽しみとして解く人、解き筋を極める愛好家、変種を楽しむ人。まず広く調べ、層に共通して愛されているものと、層ごとの違いを出す。
- **知り方**: 作り手と愛好家の公開の言葉を読む。愛されているアプリと問題集の声を読む。人に直接聞くことと、自分たちで解いて確かめることは、今回は選ばない。
- **進め方**: 愛の地図。愛されているものを 10〜20 の観点にまとめ、自作を観点ごとに評価する。測れる観点は道具で毎回確かめる。愛されている作品は、比べる相手ではなく、深掘りの材料にする。まとめは DESIGN.md にも残す。
- 4〜9 章の中身は、オーナーと 1 節ずつ合意した。10 章より後は、その合意を記録と道具の形に落としたもの。

## 4. 調べる

### 4.1 層と調べる先

- **毎日解く人**(`daily`): 新聞・雑誌のナンプレの文化と、毎日の問題を載せる媒体の考え方。毎日使われていて評価の高いアプリの説明と、その声。
- **解き筋を極める愛好家**(`expert`): パズル専門の出版社の考え方(手で作る問題、解き筋の美しさ)。作家・競技者の言葉、手筋の解説。愛好家に評価の高いアプリの作り手の言葉。
- **変種を楽しむ人**(`variant`): 変種を解説する動画の作り手と、その道具の作り手。変種の作家の言葉。
- **愛されているアプリと問題集の声**: 評価の高いアプリ(特に広告の無いもの、愛好家が勧めるもの)のストアのレビューと、紙の問題集の公開されているレビュー。何が褒められ、何が嫌われているかを拾う。声の主の層が分かれば、その層として記録する。

具体的な調べる先(名前と URL)は、非公開の `NumberPlace/quality/love/sources.md` に置く。この仕様は公開のリポジトリにあるので、他社の作品名をここには書かない。

### 4.2 やり方

- 層ごとに調べる係を立て、並べて走らせる。係は Web の公開の文章とレビューを読む。
- 使わないもの: reddit、ログインが要る所、紙の本の中身。
- 1 つの所見は、1 つの出典から読み取った 1 つの事柄にする。
- 引用は短くする(15 語未満、1 つの所見に 1 つまで)。ほとんどは要約にする。
- 係の読み(解釈)は、要約と分けて書く。
- 所見の数の目安は、層ごとに 15〜30 件、全体で 60〜120 件。
- 商標の語(`rights_terms.json` の語)は、出典の題や要約に出てきてよい。非公開の記録の中に留め、利用者に見える文(DESIGN.md、ストア、アプリ、Web)には持ち出さない。

所見の記録の形は 10.1。

## 5. 観点にまとめる(地図)

- 所見から、愛されているものを 10〜20 の観点にまとめる。
- 愛を損なうもの(例: 推測しないと進めない問題、考える時間を奪う広告や催促)は、観点の裏返し(`harms`)として、その観点の中に残す。
- 各観点に書くもの:
  - 名前と説明(何が、なぜ愛されているか)
  - 根拠の所見(2 つ以上。出典の発信者が 2 つ以上別であること)
  - 裏返し(それを損なうものと、その根拠の所見。無ければ空)
  - 愛されている例(その観点にどう応えている作品があるか。根拠の所見つき)
  - 確かめ方(8 章)
- 層と強さは、手で書かずに、根拠の所見から計算する。
  - 層: 根拠の所見の層の集まり(`any` は数えない)。
  - 強さ: 層の数を L、別々の発信者の数を S として、L が 3 か S が 5 以上なら「強」、L が 2 か S が 3 以上なら「中」、それ以外は「弱」。
- **見落としの点検**: 観点ができたら、旧方針で作った機能表の下書き(44 行)と突き合わせる。各行について、当たる観点か、当たらない理由を記録する。下書きは点検表としてだけ使い、根拠には使わない。

## 6. 自作を評価する

- 観点ごとに、今の NumberPlace を次の段で判定する。
  - `meets`(応えている)
  - `lacks`(足りない。無い、または弱い)
  - `violates`(反している。その観点の裏返しに当たる)
  - `unverified`(未確認。根拠を示せない。判定には数えない)
- 判定には根拠を付ける。根拠は次のどれか 1 つ以上。
  - 画面の写し: 測定用のエミュレータで自作を操作して撮り、縮小して保存する。
  - コードの場所: ファイルと行。
  - 確かめた手順と、その結果。
  - 測った値: 8 章の測定の記録。
- `lacks` と `violates` には、直し方の案と、手間の大きさの目安(`small` / `medium` / `large`)を付ける。
- **2 人で別々に評価する**。
  - A は統括(Claude)。
  - B は別の係。B に渡すのは、地図(所見と観点)と自作だけで、A の評価は見せない。
  - 同じエミュレータを使うので、A と B は順に行う。
  - 突き合わせ: 段が食い違った観点は確かめ直し、最終の段と、そう決めた理由を残す。A と B の段は消さずに残す。
- 愛されている例(5 章)は、比べる相手ではなく、「その観点にこう応えている例」として評価の隣に並べる。
- これまでに分かっていること(出題約 0.5 秒、起動 1.6〜2.4 秒、数字ごとの残りの数が無い、ヒントの理由の帯が数字のボタンに重なる、など)は、A だけが手がかりに使う。B には渡さない。B が同じ欠けを自分で見つけるかどうかも、評価の確かさの手がかりになる。根拠は評価のときに撮り直す。

## 7. オーナーの線

- 評価が出そろったら、観点ごとにオーナーが決める。
  - `pursue`(追う)
  - `skip`(追わない)
  - `hold`(保留)
- 統括は観点ごとに、推奨とその理由を出す。推奨の材料は 4 つ。
  - 愛の強さ(5 章の計算)
  - 自作の方針との合い方(DESIGN.md、広告を出さない買い切り、静かな遊び)
  - 評価の段
  - 直す手間
- `violates` の観点は、原則として `pursue` を推奨する。直さないと決める場合も、理由を残す。
- 聞き方: オーナーは別の端末で読むことがあり、表が見えない。そのため、質問の文の中に、観点の名前・自作の段・推奨とその理由を書く。1 回に 4 件までにする。
- 決定・日付・理由を記録する。`skip` も理由ごと残し、後で考え直せるようにする。
- `pursue` で、確かめ方が機械の観点は、目標もこのときに決める(8 章)。
- 統括は、`pursue` の観点を直す順の案を出す(愛の強さと手間から)。自作のコードを直す作業は、この仕様には含めない。線を引いた後に、別の計画を立てる。

## 8. 測れる観点を道具にする

### 8.1 確かめ方

観点ごとに、確かめ方を次のどれかに決める。

- `machine`(機械で確かめる)
- `human`(人が見る)
- `both`(両方)

### 8.2 機械の確かめ

目標は、他のアプリとの比較ではなく、根拠から決める絶対の値にする。

- **速い確かめ**(`command`): gate を走らせるたびに行う。アプリのディレクトリで命令を走らせ、終了コード 0 なら目標を満たす。
  - Dart のテストで確かめる場合、テストは `NumberPlace/love_test/` に置く。`flutter test` の既定の対象(`test/`)と分けるためで、未達の観点が gate の `test` 検査を落とさないようにする。
  - 時間の上限は既定で 600 秒。観点ごとに変えられる。
- **遅い測定**(`measure`): エミュレータで測る起動や出題の時間。gate の外で、測定の道具(11.4)で測って記録する。
  - gate は記録を読み、次の 2 つを満たせば目標を満たすとする。
    - 今のコードで測った記録である(8.4)。
    - 値が目標(`max` または `min`)を満たす。
  - 古いコードで測った記録なら fail にする。

### 8.3 人の確かめ

- 確かめる手順を記録に書き、assessment.md に出す。
- ストアに出す前に、人(オーナー、またはオーナーが頼んだ人)が手順どおり見て、日付・commit・誰が・結果(`pass` / `fail`)を残す。Claude がエミュレータで代わりに見たものは、人の確かめに数えない。
- gate は、今のコードに対する `pass` の記録があるかを見る。無い、古い、`fail` のどれかなら fail にする。開発の途中でコードが変わると記録は古くなり、gate の `love` は fail になる。出す前に見直せば pass に戻る。

### 8.4 「今のコード」の決め方

遅い測定の記録(8.2)と、人の確かめの記録(8.3)が、今のコードに対するものかを決める規則。速い確かめは毎回走らせるので、この規則は使わない。

- アプリのコードの範囲は `lib/`、`assets/`、`android/`、`ios/`、`web/`、`pubspec.yaml`、`pubspec.lock` とする。`quality/`、`store/`、`test/`、`love_test/` は含めない。共有パッケージの版は `pubspec.lock` に入るので、範囲に含まれる。
- 記録の commit から、アプリのコードの範囲に差が無ければ、今のコードとみなす。差は作業ツリーと比べ、commit していない変更と、追跡していないファイルも差に数える。
- 次の場合は、今のコードを決められないので fail にする。
  - アプリが git のリポジトリでない。
  - 記録の commit が履歴に無い。
  - 共有をローカルで参照する上書き(`pubspec_overrides.yaml`)がある。
- 測定の道具は、アプリのコードの範囲に commit していない変更があれば、測らずに止まる。記録の commit と、測ったビルドを一致させるため。

### 8.5 gate の入れ替え

- gate の `market` 検査を外し、`love` 検査を入れる。検査は次の 7 つになる: `analyze`・`test`・`quality`・`i18n`・`rights`・`licenses`・`love`。
- `love` 検査の結果:
  - `love.json` が無いアプリは `unmeasured`(理由: 愛の地図がまだ無い)。不合格にはしないので、他の 8 作の gate は落ちない。
  - 記録の形が壊れている、またはまだ埋まっていない(10.3 の incomplete)なら fail。
  - それ以外は、`pursue` の観点を 1 つずつ確かめる。すべて目標を満たせば pass、1 つでも満たさなければ fail。
  - `skip` と `hold` の観点は確かめない。
  - 観点ごとの結果(`items`)を gate の結果に入れる。

## 9. 今あるものの扱い

### 9.1 そのまま使うもの

- gate の枠と、6 つの検査(`analyze`・`test`・`quality`・`i18n`・`rights`・`licenses`)。
- 権利の語の検査(`rights_guard.py`、`rights_terms.json`)。
- 性能の道具(`tool/perf/`)。自作の起動と出題の時間を測るのに使う。競合はもう測らない。
- ストアの文章から権利の語を外した直し(`store/play/README.md`)。

### 9.2 外すもの

- gate の `market` 検査と、その道具とテスト(`market_check.py`、`market_report.py`、`tests/test_market_check.py`、`tests/test_market_report.py`)。love に入れ替える作業の中で外す。消した後も git の履歴に残る。

### 9.3 競合の材料

対象は、10 本の一覧、機能表の下書き、台本、見本、画面の写し。比べる相手としては、もう使わない。

1. まだ commit していないもの(`quality/market/scripts/`、`quality/market/evidence/`)と、機能表の下書き(作業場にある `features-draft.json` を `quality/market/features.json` として置く)を、NumberPlace で 1 つの commit にして履歴に残す。commit のメッセージには「旧方針の記録」と書く。
2. 次の commit で、`quality/market/` を作業のファイルから外す。ただし、自作の台本(`scripts/self.json` と `scripts/refs/self-new_game.json`)は `quality/love/measure/scripts/` に移して使う。
3. 見落としの点検(5 章)では、1 の commit から機能表の下書きを読む。love.json には、その commit を記録する。

NumberPlace のリポジトリは非公開なので、競合の画面の写しを履歴に残してよい。

### 9.4 そのほか

- **これまでに分かったこと**(6 章の手がかり)は、評価で使う。根拠は撮り直す。
- **旧仕様と旧計画**は消さない。それぞれの冒頭に、この仕様に置き換えたことを 1 行足す。全体の設計の第 2 節にも、3 層目をこの仕様で置き換えたことを 1 行足す。
- **旧計画の台帳**(`.superpowers/sdd/2026-10-14-numberplace-yardstick/progress.md`)に、中止と、この仕様へ移ったことを書く。
- **stash にある、まだ通らないテスト 3 件**(競合の遅い起動を待つためのもの)は使わない。消さずに置いておく。
- **push していない commit**(twoyearsold_ui と NumberPlace)は、新しい計画が終わったときに、まとめて push してよいかをオーナーに確かめる。

## 10. 記録の形

置き場所は `NumberPlace/quality/love/`。

- `sources.md`: 調べる先の一覧(4.1)。人が書く。
- `findings.json`: 所見(単一の出所)。
- `love.json`: 観点・評価・推奨・決定・確かめ方・人の確かめの記録(単一の出所)。
- `map.md`: 地図。生成物で、手で直さない。
- `assessment.md`: 評価と線。生成物で、手で直さない。
- `evidence/a/`、`evidence/b/`: 評価の根拠の画面の写し(A と B)。自作だけ。
- `measure/`: 遅い測定の記録(`<観点の id>.json`)と、自作の台本(`measure/scripts/`)。

JSON を単一の出所にして md を生成するのは、終わりの条件(根拠の数、別々の発信者、段、決定)を機械で確かめ、gate が目標と記録を読めるようにするため。md を手で書くと JSON とずれる。

### 10.1 findings.json

```json
{
  "findings": [
    {
      "id": "f001",
      "layer": "expert",
      "channel": "words",
      "kind": "love",
      "source": "(発信者の名前)",
      "title": "(出典の題)",
      "url": "https://example.com/article",
      "read_on": "2026-10-16",
      "summary": "(要約)",
      "quote": "",
      "reading": ""
    }
  ]
}
```

- `id`: `f` と 3 桁以上の数字。重複しない。
- `layer`: `daily` / `expert` / `variant` / `any`(層を決められない)。
- `channel`: `words`(作り手と愛好家の公開の言葉)/ `reviews`(アプリと問題集の声)。
- `kind`: `love`(愛されているもの)/ `harm`(愛を損なうもの)。
- `source`: 別々の出典を数える単位(発信者)。同じ発信者の別の記事は、同じ `source` にする。
- `url`: `http://` か `https://` で始まる。
- `summary`: 空にしない。
- `quote`: 任意。空白で区切った語が 15 未満で、かつ 60 字未満。
- `reading`: 係の読み。任意。

### 10.2 love.json

```json
{
  "app": "NumberPlace",
  "aspects": [
    {
      "id": "logic_only",
      "name": "論理だけで解ける",
      "description": "推測や試し打ちをせずに、筋道だけで最後まで解けること",
      "evidence": ["f003", "f017", "f042"],
      "harms": [{"text": "推測しないと進めない問題", "evidence": ["f021"]}],
      "examples": [{"name": "(作品の名前)", "how": "(どう応えているか)", "evidence": ["f030"]}],
      "verify": "both",
      "assessment": {
        "a": {"grade": "meets", "evidence": ["code: lib/domain/generator.dart:88"]},
        "b": {"grade": "meets", "evidence": ["evidence/b/logic_only-1.png"]},
        "final": {"grade": "meets", "evidence": ["code: lib/domain/generator.dart:88"], "reconcile": ""},
        "fix": null,
        "effort": null
      },
      "recommendation": {"decision": "pursue", "reason": "(推奨の理由)"},
      "owner": {"decision": "pursue", "date": "2026-10-20", "reason": "(理由)"},
      "check": {"kind": "command", "run": ["flutter", "test", "love_test/logic_only_test.dart"], "timeout_s": 600},
      "target": null,
      "human": {
        "steps": ["(確かめる手順)"],
        "last": {"date": "2026-10-21", "commit": "abc1234", "by": "owner", "result": "pass", "note": ""}
      }
    }
  ],
  "coverage_check": {
    "checklist_commit": "(9.3 の 1 の commit)",
    "rows": [{"row": "digit_counter", "aspect": "logic_only", "note": ""}]
  },
  "fix_order": [{"id": "logic_only", "reason": "(この順の理由)"}]
}
```

- 観点の数は 10〜20。`id` は英小文字・数字・`_` で、重複しない。
- `evidence`: 所見の id。2 つ以上で、すべて実在し、`kind` が `love` で、`source` が 2 つ以上別。
- `harms[].evidence`: 1 つ以上。実在し、`kind` が `harm`。
- `examples[].evidence`: 1 つ以上。実在する。
- `verify`: `machine` / `human` / `both`。
- `assessment` の各 `grade`: `meets` / `lacks` / `violates` / `unverified`。
- 評価の根拠の文字列は、次のどれかの形にする。
  - `evidence/…`: `quality/love/` の中に実在する画面の写し。
  - `code: <path>:<行>`: アプリの中に実在するファイルと行。
  - `steps: <手順と結果>`
  - `measure: measure/<file>`: 実在する測定の記録。
- `grade` が `unverified` でなければ、根拠は 1 つ以上要る。
- `final.grade` が `lacks` か `violates` なら、`fix`(直し方の案)と `effort`(`small` / `medium` / `large`)が要る。
- `a.grade` と `b.grade` が違うとき、または `final.grade` がどちらかと違うときは、`final.reconcile` に理由が要る。
- `recommendation.decision` と `owner.decision`: `pursue` / `skip` / `hold`。`reason` は空にしない。`owner.date` は日付。
- `owner.decision` が `pursue` のとき:
  - `verify` が `machine` か `both` なら `check` が要る。
    - `{"kind": "command", "run": [...], "timeout_s": 600}`
    - `{"kind": "measure", "tool": "launch_time" | "new_game", "metric": "median_ms"}`。このときは `target`(`{"max": <数>}` か `{"min": <数>}`)も要る。
  - `verify` が `human` か `both` なら `human.steps` が要る。
- `human.last`: 人の確かめの記録。`result` は `pass` / `fail`。`commit` はその時のアプリの commit。
- `coverage_check.rows`: 機能表の下書きの各行に、当たる観点の id か、当たらない理由(`note`)を書く。
- `fix_order`: `pursue` の観点の id を直す順に並べ、理由を付ける。

### 10.3 壊れている(broken)と、まだ(incomplete)

形の検査は、理由を 2 種類に分けて出す。

- **broken**: 決まった値の外、参照先の所見や写しが無い、型が違う、など。生成物は作らない。
- **incomplete**: 生成物は作れるが、終わりの条件(17 章)をまだ満たしていない。例: 評価が無い、最終の段が `unverified`、決定が無い、`pursue` なのに確かめ方が無い、観点の数が 10〜20 の外、根拠が 1 つ、発信者が 1 つ。生成物は作り、まだの所を「未」と出す。

gate は、どちらも fail にする。作業の途中でも、地図だけ先にオーナーへ見せられるようにするため、生成は incomplete でも止めない。

### 10.4 測定の記録 measure/<観点の id>.json

```json
{
  "aspect": "quick_start",
  "tool": "launch_time",
  "metric": "median_ms",
  "value": 1450,
  "runs": [1400, 1450, 1500],
  "status": "ok",
  "reason": "",
  "commit": "abc1234",
  "measured_at": "2026-10-21T10:00:00+09:00",
  "load_avg_1m": 3.2,
  "device": {"avd": "yardstick_play_35", "image": "android-35 google_apis_playstore arm64-v8a"}
}
```

`status` が `unmeasured` の記録は、目標を満たさないとみなす。

## 11. 道具

共有パッケージ `twoyearsold_ui/tool/` に置く。他の 8 作に広げるときも、同じ道具を使う。

### 11.1 love_check.py

- 所見と love.json の形を検査し、broken と incomplete の理由を分けて返す。
- 5 章の層と強さを計算する。
- 8.4 の「今のコード」を決める。
- `pursue` の観点を確かめ、観点ごとの結果を返す。
- gate から呼ばれる。単独でも走らせられる。

### 11.2 love_report.py

- `python3 twoyearsold_ui/tool/love_report.py <App>` で、map.md と assessment.md を作る。
- broken があれば作らず、理由を出して exit 2。
- 生成物の冒頭に、生成物であることと、元のファイルを書く。
- 表は使わず、見出しと箇条書きで書く(オーナーが別の端末で読むため)。
- **map.md**: 観点ごとに、名前・説明・層・強さ・根拠(要約・発信者・URL)・裏返し・愛されている例・確かめ方を出す。末尾に見落としの点検の結果を出す。
- **assessment.md**: 観点ごとに、次を出す。末尾に直す順の案を出す。
  - 最終の段、A と B の段、根拠、突き合わせの理由
  - 直し方の案と手間
  - 推奨とオーナーの決定
  - 目標、人の確かめの手順と記録
  - 最新の gate の結果(`quality/gate.json` の `love` の `items`)

### 11.3 gate.py の変更

- `market` を外し、`love` を入れる(8.5)。
- 結果の JSON の `love` の行に `items`(`[{"id", "status", "detail"}]`)を足す。人が読む表には、`love` の下に観点ごとの結果を並べる。

### 11.4 love_measure.py

`python3 twoyearsold_ui/tool/love_measure.py <App> <観点の id>`

1. 観点の `check` が `measure` であることを確かめる。
2. アプリのコードの範囲に commit していない変更が無いこと、上書き(`pubspec_overrides.yaml`)が無いことを確かめる。あれば止まる。
3. Mac の負荷(load average の 1 分値)が上限を超えていれば、測らずに止まる。上限の値は、計画の最初に確かめて決める(12 章の 4)。
4. 今のコードを release でビルドし、測定用のエミュレータに入れ直す。
5. 性能の道具(`launch_time.py` か `new_game.py`)を、`quality/love/measure/scripts/` の台本で走らせる。
6. 結果に、commit・日時・負荷・端末を付けて、`measure/<観点の id>.json` に書く。

性能の道具そのものは変えない。結果の JSON を標準出力の最後の行に出す今の形を読む。

## 12. 未検証の前提

計画では、これらを確かめる作業を先に置く。

1. 層ごとに十分な所見(15 件以上)が、公開の文章とレビューから集まる。特に、日本の雑誌の読者の声と、変種の層。集まらない層は、そのことを地図に書く。少なさは強さの計算に表れる。
2. ストアのレビューを、ログインなしでどこまで読めるか。ストアの Web のページは、レビューの一部しか出さない。
3. 機械で確かめられる観点が出てくる。全部が人の確かめになっても、love 検査は形の検査と人の記録で成り立つ。
4. エミュレータでの測定は、Mac の負荷で揺れる。前回は、同じ自作の起動が 1.6 秒の回も 24 秒の回もあった。負荷の上限を決め、上限の下で測った値の揺れが、目標の判定を変えない程度に収まるかを確かめる。
5. 自作の台本(`self.json`)に、起動の速さを測るための最後の画面の場所(`ready_region`)があるか。無ければ足す。
6. 今のコードの release ビルドを、測定用のエミュレータに入れ直せる(前に入れた版と署名が合わない場合は、入れ直しの手順を決める)。鍵とそのパスワードはリポジトリの外(`~/keystores/`)のまま扱い、表示しない。
7. `flutter test love_test/<file>` が、`test/` の外でも動く(`test/` にある設定に頼らずに書ける)。

## 13. 失敗の扱い

- 黙って合格にしない。確かめられないものは fail か `unmeasured` にし、理由を出す。
- `love.json` が無ければ `unmeasured`。
- 形が壊れている、またはまだ埋まっていなければ fail。理由は 10 件まで並べ、残りは件数で出す。
- 速い確かめの命令が無い、時間切れ、終了コードが 0 でない場合は、その観点を fail にする。
- 測定の記録が無い、古い、`unmeasured`、目標に届かない場合は、その観点を fail にする。
- 人の確かめの記録が無い、古い、`fail` の場合は、その観点を fail にする。
- 今のコードを決められない場合(8.4)は、その観点を fail にする。

## 14. 確かめ方(テスト)

- **love_check**: 一時ディレクトリに見本の findings.json と love.json を作り、各規則の境目を当てる。例: 根拠 1 つ、同じ発信者 2 つ、観点 9 個と 21 個、`lacks` で直し方の案が無い、`pursue` で確かめ方が無い、broken と incomplete の分け方。強さの計算の境目も当てる。
- **今のコードの決め方**: 一時ディレクトリに git のリポジトリを作り、次を当てる。
  - 記録の後に `lib/` を変える。
  - commit していない変更がある。
  - 追跡していないファイルがある。
  - `quality/` だけを変える(有効のまま)。
  - `pubspec_overrides.yaml` を置く。
  - 記録の commit が履歴に無い。
- **gate**: `love` の行と `items` が出る。`love.json` が無いと `unmeasured`。`market` の行が無い。
- **love_report**: 生成物に、観点の名前・強さ・段・決定が出る。broken のときは書かずに exit 2。incomplete のときは「未」と出して書く。
- **love_measure**: 偽の命令(`flutter`・`adb`・性能の道具)で、作業ツリーが汚れていると止まる、負荷が高いと止まる、記録に commit と負荷が残る、を当てる。
- 道具は Python 3.9 で動き、テストは今の共有の道具(`tool/tests/`)と同じ形で走らせる。

## 15. 進め方

★はオーナーの番。

1. 未検証の前提(12 章)のうち、道具に関わるもの(4〜7)を確かめる。
2. 道具を作る(love_check・love_report・love_measure・gate の入れ替え)。競合の材料を履歴に残して外す(9.3)。
3. 調べる先の一覧(sources.md)を作り、層ごとの係を並べて調べる(4 章)。
4. 観点にまとめ、見落としを点検する(5 章)。
5. ★ 地図(map.md)を見て、観点に過不足が無いかを確かめる。
6. 自作を A と B で別々に評価し、突き合わせる(6 章)。
7. ★ 推奨を見て、観点ごとに線を引く。機械で確かめる観点は目標も決める(7 章)。
8. `pursue` の観点の確かめを用意する(速い確かめのテスト、測定、人の確かめの手順)。gate を走らせ、観点ごとの結果を出す。直す順の案を出す。
9. ★ DESIGN.md への反映の案を見て、承認する(16 章)。
10. 旧仕様・旧計画・全体の設計に置き換えの 1 行を足し、旧計画の台帳に中止を書く。

5 は、オーナーとの合意の外で足した確かめ(地図ができた所で、評価に入る前に一度見てもらう)。不要なら飛ばす。

## 16. DESIGN.md への反映

- ナンプレに限らず全作に通じる観点(例: 静けさ、考える時間を奪わないこと)は、DESIGN.md の共通の規範(§0〜§10 の該当する所)に短く足す案を作る。
- NumberPlace だけに当てはまる観点は、§10.5(個性を殺さない)に NumberPlace の項を設けて足す案を作る。
- どちらも全アプリの規範を変えるので、案と差分をオーナーに見せ、承認された分だけ書く。
- 商標の語は持ち込まない。
- DESIGN.md(`twoyearsold/DESIGN.md`)は版管理の外にある。書き換える前に、今の DESIGN.md の写しを運用のリポジトリ(`twoyearsold-ops`、非公開・版管理あり)の `docs/design-md/` に commit して残す。

## 17. 終わりの条件

- findings.json があり、形の検査で broken が無い。層ごとの所見の数が分かる。
- love.json に 10〜20 の観点があり、各観点に、別々の発信者 2 つ以上の根拠がある。
- すべての観点に、最終の評価の段(`unverified` 以外)とその根拠がある。A と B の段が残り、食い違いには理由がある。
- すべての観点に、オーナーの決定(`pursue`・`skip`・`hold`)と、日付と理由がある。`pursue` の観点には、確かめ方に応じた `check`・`target`・`human.steps` がある。
- 直す順の案(`fix_order`)がある。
- gate の `market` が `love` に替わり、NumberPlace で gate を走らせると、`love` の行に観点ごとの結果が出る。目標に届かない観点は残っていてよい(直しの計画の材料になる)。
- 競合の材料が履歴に残り、作業のファイルから外れている。自作の台本は `quality/love/measure/scripts/` にある。
- map.md と assessment.md が生成されている。
- DESIGN.md への反映の案をオーナーに見せ、承認された分を書いた。
- 旧仕様・旧計画・全体の設計に置き換えの 1 行があり、旧計画の台帳に中止の行がある。

## 18. 含めないもの

- 自作のコードの直し。線を引いた後に、別の計画を立てる。ただし、評価のために自作を動かして撮ること、確かめのテスト(`love_test/`)を書くことは含む。
- 他の 8 作への展開。NumberPlace でやり方が固まってから行う。
- 人に直接聞くこと、自分たちで解いて確かめること。
- 競合の性能の比較。
- 実機での測定。測定はエミュレータで行う。
- 無人の運転。
