# 物差し(NumberPlace で縦に通す) 設計

2026-10-14。全体監査(`twoyearsold-ops/docs/audit/2026-10-14-ecosystem-audit.md`)を受けたオーナーの決定「次に作るのは物差しとアプリの改良」に基づく。全体の設計(`2026-10-14-ecosystem-design.md`)の第 4 節(品質の 3 層)のうち、第 1 層の残りと第 3 層を、まず NumberPlace 1 本で具体化する。

## 1. 目的

「品質を極める」「市場に対して相対的に最も高い性能と、機能・モードの網羅」を、測れる形にする。測った結果の欠けが、そのまま次の改良の材料になる。

この仕様の範囲は「物差しを作り、NumberPlace を測り、欠けの一覧を出し、オーナーに線を引いてもらう」まで。欠けを埋める改良そのものは、線が引けた後に、まとまりごとに別の計画で進める。

## 2. オーナーの決定(2026-10-14)

| 項目 | 決定 |
|---|---|
| 順番 | NumberPlace 1 本で縦に通し、できた形を他の 8 作に広げる |
| 網羅の線 | Claude が競合の機能とモードを洗い出し、「網羅する/哲学に反するので外す/見た目や遊び方が変わるのでオーナーに伺う」に根拠つきで仕分ける。オーナーは一覧を一度見て線を引く。以後の改良は線の内側を埋める |
| 性能の測り方 | Android のエミュレータで測る。エミュレータの Play ストアへのログインと、競合のインストールはオーナーが行う |
| 出題の時間の測り方 | 起動の速さは全アプリを自動で測る。出題の時間は、競合ごとに台本を作り、録画のコマから割り出す。台本が壊れたアプリは「未計測」と出す |
| 作業の形 | 見張りのある作業(対話の場から、担当と確認役で)。無人の運転は専用機を用意してから |

## 3. 前提(Claude が置いたもの。オーナーが設計の対話で確認済み)

- 競合は、日本と米国の Google Play と App Store で「ナンプレ・数独」の上位から 10 本選ぶ。性能の比較は Android にあるものだけ。App Store にしか無いものは、機能の比較だけにする。
- 性能の物差しは「起動の速さ」と「新しい問題が盤に出るまでの時間(出題の時間)」。同じエミュレータで何回か測った中央値で比べる。
- 合格は全体の設計 4.3 のとおり: 線の内側の機能とモードをすべて持ち、性能の各項目で競合の最良値を上回ること。

## 4. 作るもの

### 4.1 第 1 層の入口 `twoyearsold_ui/tool/gate.py <アプリ>`

共有の道具。今の横断ガード(`quality_guard.py`)と同じ場所に置く。

- アプリ名を渡すと、そのアプリで次を順に走らせる。
  1. `flutter analyze`
  2. 全テスト(`flutter test`。ゴールデンとタップ領域の巡回を含む)
  3. 横断ガード(`quality_guard.py`)のそのアプリの列
  4. 翻訳ガード(`i18n_guard.py`)
  5. 権利の語の検査(4.2)
  6. ライセンス表示の確認(設定画面のコードに、共有の `LicensesScreen` を開く入口があること。コードを読んで確かめる)
  7. 第 3 層の記録の形の検査(4.3 の JSON が決めた形どおりか。記録がまだ無いアプリは「未計測」)
- 結果は、機械が読める JSON と、人が読む表の両方で出す。1 つでも不合格なら、終了コードで知らせる。

```json
{
  "app": "NumberPlace",
  "ok": false,
  "checked_at": "2026-10-15T10:00:00+09:00",
  "checks": [
    {"name": "analyze", "status": "pass", "detail": "", "seconds": 12.3},
    {"name": "rights", "status": "fail", "detail": "store/play/listing/en-US/full.txt:3 Sudoku", "seconds": 0.1}
  ]
}
```

`status` は `pass` / `fail` / `unmeasured`(理由を `detail` に書く)。道具が見つからないときは `fail`。

### 4.2 権利の語の検査

- 使ってはいけない語の辞書を `twoyearsold_ui/tool/rights_terms.json` に置く。

```json
{
  "terms": [
    {"term": "Sudoku", "forms": ["sudoku", "数独", "スドク", "스도쿠", "Судоку"], "reason": "他社の商標(日本の数独)。名前に使わない方針"}
  ]
}
```

- 初期の語は Sudoku・数独・Othello・オセロ・Gobblet・Tetris。それぞれ、37 言語での書き方を `forms` に入れる。
- 調べる先は、利用者に見える所だけ: 表示文言(`lib/l10n/*.arb`)、ストアの掲載文(`store/**`)、Web の文面(`web/*.html`、`web/manifest.json`、`game.json`)。
- コードの中の名前(`sudoku_variant.dart` など)は利用者に見せないので対象外。
- 大文字小文字を区別せず、語の一部として含まれる場合も見つける。

### 4.3 第 3 層の記録 NumberPlace の `quality/market/`

アプリと一緒に版を管理する。

- `competitors.json`

```json
{
  "chosen_on": "2026-10-15",
  "criteria": "日本と米国の Google Play と App Store で「ナンプレ・数独」の上位",
  "apps": [
    {"id": "c01", "name": "(例)ナンプレのアプリ A", "play": "com.example.app", "app_store": null,
     "price_model": "free_with_ads", "rating": 4.7, "ratings_count": 120000,
     "why": "日本の Play で無料の上位 1 位", "on_android": true}
  ]
}
```

- `features.json`(行が機能・モード、列が競合と自作)

```json
{
  "features": [
    {"id": "notes", "name": "メモ(候補の書き込み)", "kind": "feature",
     "has": {
       "self": {"value": "yes", "evidence": "evidence/self/notes.png"},
       "c01": {"value": "yes", "evidence": "evidence/c01/notes.png"}
     },
     "proposal": {"decision": "cover", "reason": "競合 9/10 が持つ。盤の操作の基本", "exclude_category": null},
     "owner": {"decision": null, "date": null, "note": ""}}
  ]
}
```

  - `kind`: `feature`(機能)/ `mode`(遊び方)/ `variant`(変種)/ `setting`(設定)。
  - `value`: `yes` / `no` / `unknown`。根拠(`evidence`)の無い升は `unknown` とし、「ある」とは数えない。
  - `proposal.decision`: `cover`(網羅する)/ `exclude`(外す)/ `ask`(オーナーに伺う)。`exclude` のときは `exclude_category` に `ads` / `iap` / `online` / `trademark` / `philosophy` のどれか。
  - `owner.decision`: オーナーが線を引いた結果(`cover` / `exclude`)と日付。

- `perf.json`

```json
{
  "device": {"avd": "yardstick_play_35", "image": "android-35 google_apis_playstore arm64-v8a", "host": "MacBook Pro M5 Pro / 24GB"},
  "measured_on": "2026-10-15",
  "conditions": {"new_game": "Classic・9×9・中くらいの難しさ"},
  "apps": {
    "self": {
      "cold_start_ms": {"runs": [412, 398], "median": 405, "status": "ok", "reason": ""},
      "new_game_ms": {"runs": [120, 118], "median": 119, "status": "ok", "reason": ""}
    }
  }
}
```

  - `status`: `ok` / `unmeasured`(理由を `reason` に書く)。

- `README.md`: 上の 3 つから作る、人が読むまとめ(一覧表、欠け、性能の比較)。
- `evidence/`: 根拠の画面の写し。縮小して保存する。非公開のリポジトリの中だけで使い、外には出さない。
- `scripts/`: 競合ごとの出題の台本(4.4)。

### 4.4 性能の道具 `twoyearsold_ui/tool/perf/`

共有。他の 8 作でも使う。

- **起動の速さ**: アプリを止めてから(`am force-stop`)起動し(`am start -W`)、最初の画面が出るまでの時間を取る。11 回測り、最初の 1 回を捨てた 10 回の中央値をとる(初回だけの準備の時間を除くため)。
- **出題の時間**: 競合ごとの台本(どこを順に押すか、盤のある場所)を `quality/market/scripts/<id>.json` に置く。端末の録画(`screenrecord`)を回しながら台本どおりに押し、最後に押した瞬間から、録画のコマで盤の場所が描かれて落ち着くまでの時間を ffmpeg で割り出す。5 回測って、その中央値をとる(捨てる回は無い)。
  - 条件は「Classic・9×9・中くらいの難しさ」にそろえる。そろえられない競合は、近い条件を `perf.json` の理由欄に書く。
  - 自作も同じ方法で測る。
  - 競合の広告による遅れも、利用者が実際に待つ時間なので、そのまま含める。
- 台本が壊れた(押す場所が見つからない、盤が現れない)アプリは `unmeasured` とし、全体は止めない。

```json
{
  "app": "c01",
  "package": "com.example.app",
  "steps": [
    {"tap": {"text": "New Game"}},
    {"tap": {"text": "Medium"}}
  ],
  "board_region": {"x": 40, "y": 600, "w": 1000, "h": 1000}
}
```

  - `tap` は、画面の文字(`text`)か、座標(`x`, `y`)で指定する。文字で指定した場合は、`uiautomator dump` で場所を探す。

### 4.5 測定用のエミュレータ

- 今のエミュレータ(`np`)は Play ストアの無い種類(`google_apis`)。
- Google 公式の Play ストア入りのシステムイメージ(`system-images;android-35;google_apis_playstore;arm64-v8a`、約 1.5GB)を `sdkmanager` で入れ、測定用のエミュレータ `yardstick_play_35`(Pixel 7 相当)を作る。
- この取り込みは、この仕様の承認をもって行う。

### 4.6 欠けを台帳へ

オーナーが線を引いた後、線の内側で足りないものを、運用リポジトリの `ledger/NumberPlace.md` の「課題」に根拠つきで書く。

```
- [market] 競合 7/10 が持つ「〇〇」が無い(根拠: quality/market/features.json の 〇〇)
- [perf] 出題の時間が競合の最良値(c03 の 210ms)を上回っていない(自作 340ms)(根拠: quality/market/perf.json)
```

## 5. 進め方

★はオーナーの番。

1. 入口(4.1)と権利の語の検査(4.2)を作り、NumberPlace で走らせる。落ちた所は直す。直しが見た目や文言を変える場合は、オーナーに伺う。
2. 競合の候補 10 本を、日米の Play と App Store の上位から根拠つきで選ぶ。
3. 測定用のエミュレータを作る(4.5)。
4. ★ エミュレータで Google にログインし、候補のうち Android にある無料のものを Play から入れる。候補の一覧はこのとき見せ、入れ替えたいものがあれば入れ替える。有料の競合は買わず、機能は掲載情報から比べる。
5. 各競合を実際に触って、機能とモードを根拠つきで洗い出す。台本を作り、起動の速さと出題の時間を測る。自作も同じ方法で測る。
6. 仕分けとまとめ(README)を作る。自作の掲載文の言い過ぎ(たとえば「デイリーチャレンジ」が実在するか)も、ここで洗い出す。
7. ★ 一覧を見て、一度だけ線を引く。
8. 線の内側の欠けを台帳に書く(4.6)。改良そのものは、まとまりごとに別の計画を立てる。

## 6. 失敗の扱い

- どの道具も、項目ごとに「合格/不合格/未計測(理由)」を出す。黙って合格にしない。道具が見つからない場合は不合格。
- エミュレータが動いていなければ、測定は理由を出して止まる。
- 根拠の無い升は「不明」として数え、「ある」とは扱わない。

## 7. 確かめ方

- 入口と権利の語の検査: 小さな見本のアプリの形(一時ディレクトリ)を作り、偽の命令(`flutter` など)で走らせてテストする。
- 録画の解析: 盤が決まったコマで現れる人工の画像の並び(と、それから作った動画)を作り、前後 1 コマ以内で当てられることを確かめる。
- 記録の形: `competitors.json`・`features.json`・`perf.json` の形の検査を作り、入口に含める。
- 道具は Python 3.9 で動き、テストは今の共有の道具と同じ形で走らせる。

## 8. 終わりの条件

- 入口が NumberPlace で走り、結果が残っている(落ちた所は直したか、課題になっている)。
- 権利の語の辞書があり、NumberPlace に引っかかる語が無い。
- 競合 10 本が理由つきで選ばれ、機能の一覧表が根拠つきで埋まっている。
- 起動の速さは、Android の競合すべてと自作で測れている。出題の時間は 7 本以上で測れていて、残りは理由つきで「未計測」になっている。
- オーナーの線が記録され、欠けが台帳にある。

## 9. 含めないもの

- 第 2 層(エミュレータでの崩れの巡回)。
- 他の 8 作への展開(この形ができてから)。
- iOS での性能の比較。
- 欠けを埋める改良そのもの。
- 無人の運転。

## 10. 未検証の前提

実装の計画では、これらを確かめる作業を先に置く。

1. Play ストア入りのエミュレータで Google にログインでき、競合を入れられる(端末の確かめで入れられないアプリがありうる)。
2. `am start -W` の時間が、アプリごとに同じ意味で比べられる(起動の画面の作りがアプリごとに違う)。比べにくい場合は、録画から「最初の操作できる画面」までの時間で測り直す。
3. 録画のコマから、出題の時間を前後 1 コマ(約 17〜33ms)の精度で割り出せる(エミュレータの録画はコマの間隔が一定でない)。
4. 競合の広告による揺れが、中央値で吸収できる程度に収まる。
5. 10 本 × 15 回の測定が、現実的な時間で終わる。
